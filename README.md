# TAPRIME

Мультитенантный сервис для автоматизации задач и служебных записок.

## Phase 0 — каркас (готово)

- Модели: `Company`, `Department`, `User` (роль хранится как enum: superadmin / company_admin / org_head / dept_head / employee)
- Тенант-изоляция: `company_id` всегда берётся из JWT-токена, а не из запроса — один тенант физически не может обратиться к данным другого
- Авторизация: `POST /auth/login` (email + пароль) → JWT, `GET /auth/me`
- Платформенные эндпоинты (только для суперадмина): `POST /platform/companies` — создать компанию-клиента + её первого администратора одним запросом (ручной онбординг)
- Внутри компании (доступно администратору компании): `POST /departments`, `POST /users`
- При первом старте приложение само создаёт суперадмина платформы (email/пароль — из переменных окружения `FIRST_SUPERADMIN_EMAIL` / `FIRST_SUPERADMIN_PASSWORD`)

## Phase 1 — Служебные записки (готово)

- **Конструктор шаблонов** (`POST /memo-templates`, только администратор компании): у каждого вида служебной записки свой набор полей (текст с ограничением длины / число / валюта KZT-USD-EUR) и своя цепочка согласующих с дедлайном (в часах) на каждый шаг
- **Создание записки** (`POST /memos`): сотрудник выбирает вид записки и заполняет поля по шаблону; значения валидируются против конструктора (обязательность, тип, макс. длина)
- **Последовательное согласование**: шаги согласования материализуются из шаблона при создании записки. Активен всегда только один шаг (`status=pending`) — согласующий следующего шага не видит записку вообще (ни в списке, ни по прямой ссылке), пока не отработает предыдущий. Проверено на реальных данных в PostgreSQL — см. ниже
- **Дедлайны и просрочка**: у каждого шага свой срок (`deadline_at`), считается от момента, когда шаг стал активным. Фоновая задача (APScheduler, каждые 15 минут) находит просроченные активные шаги и один раз уведомляет согласующего и автора (`Notification`). `deadline_at` не сдвигается — насколько шаг просрочен, видно как `now() - deadline_at`, это и есть «счётчик в минус»
- **Отчёт** (`GET /reports/overdue`, администратор/руководитель организации): список сейчас просроченных шагов с указанием, на сколько часов — «кто тормозит процесс»
- **Уведомления** (`GET /notifications`, `POST /notifications/{id}/read`): пока только внутриплатформенные (в базе); email/SMS — Phase 4, когда определимся с провайдером

Эндпоинты: `GET/POST /memo-templates`, `GET /memo-templates/{id}`, `POST /memos`, `GET /memos/mine`, `GET /memos/pending-approval`, `GET /memos/{id}`, `POST /memos/{id}/decide`.

## Запуск через Docker (рекомендуется, в том числе на боевом сервере)

```bash
cp backend/.env.example backend/.env
# отредактируйте backend/.env — особенно SECRET_KEY и FIRST_SUPERADMIN_PASSWORD
docker compose up --build
```

API будет доступен на `http://localhost:8000`, документация (Swagger) — на `http://localhost:8000/docs`.

## Проверка вручную (curl)

```bash
# логин суперадмином платформы
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@taprime.local","password":"<пароль из .env>"}'

# создать первую компанию + администратора компании (подставьте токен из ответа выше)
curl -X POST http://localhost:8000/platform/companies \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"ООО Ромашка","admin_email":"admin@romashka.kz","admin_password":"strongpass123","admin_full_name":"Иван Иванов"}'
```

Дальше — логин администратором компании, создание пользователей-согласующих (`POST /users`), создание шаблона (`POST /memo-templates`) и записки (`POST /memos`) — по Swagger-документации `/docs`.

## Важное примечание по проверке в этой сессии

В песочнице, где писался код, нет доступа к PyPI/apt (сетевые ограничения окружения), поэтому запустить сам FastAPI-сервер здесь не удалось. Что было реально проверено вместо этого:

- Весь код проходит `python -m py_compile` без синтаксических ошибок
- Полная DDL-схема обеих миграций (`0001_initial`, `0002_memo_module`) выполнена на реальном локальном PostgreSQL 16 без ошибок — таблицы, внешние ключи (включая циклическую зависимость departments.head_user_id ↔ users), индексы, enum-типы, JSONB-колонка для значений полей записки
- На тестовых данных проверены ограничения Phase 0 (уникальность email, каскадное удаление, тенант-изоляция) и весь workflow согласования Phase 1: создание записки → согласующий 2-го шага не видит её, пока не отработал 1-й → согласование 1-го шага активирует 2-й → полное согласование меняет статус записки → отдельно проверен расчёт просрочки (шаг с дедлайном в прошлом корректно попадает в отчёт с правильным числом часов просрочки)

На боевом сервере (где будет обычный доступ в интернет) нужно один раз прогнать `docker compose up --build` — там уже будет полноценная проверка живого приложения, включая сами HTTP-эндпоинты.
